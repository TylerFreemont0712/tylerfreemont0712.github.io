ファイルシステム系のMCPサーバは、たいてい40行程度で書けます。`read_file`、
`list_dir`、`write_file`を公開し、パスを結合し、ツールスキーマをモデルに渡せば動きます。
デモ用のリポジトリでも自分のプロジェクトディレクトリでも問題なく動作します。
そして、日本語のファイル名が並んだディレクトリを指定した瞬間に壊れます。

上がってくる不具合報告は、一見して意味が通りません。
**「エージェントがファイルが存在しないと言うが、直前に自分で出力した一覧に載っている」**

## 見た目が同じで、文字列としては別物

直接の原因はUnicodeの正規化です。`が`は1つのコードポイント（U+304C）で表すことも、
`か`（U+304B）と結合文字の濁点（U+3099）の2つで表すこともできます。両者は正規等価であり、
表示は完全に一致します。日本語を読む人間はどちらも同じ文字だと判断します。
しかし文字列としては一致しません。

macOSは従来、ファイル名をNFDに近い分解形で保持してきました。WindowsとLinuxは基本的に
作成したアプリケーションが渡した形をそのまま保持し、実際にはNFCになることが多いです。
つまり、Macで作成したファイルをLinuxから共有経由で読むと、利用者が入力した名前と
`==`で一致しないファイル名が返ってきます。

これがバグの全体像です。`list_dir`が分解形を返し、モデルはそれをそのまま`read_file`に
渡し、スタックのどこか——あるいはファイルシステム自身——が合成形と比較して
「そのようなファイルはない」と応答します。モデルはモデルらしく、
パスを少し間違えたのだろうと解釈して再試行します。そして再試行を繰り返します。
毎回正しいファイル名を打ち直しながら、小さなモデルが十数ターンを費やす様子を
実際に見たことがあります。

対処は地味です。境界で正規化し、形式を1つに決めることです。

```python
import unicodedata
from pathlib import Path

def canon(p: str | Path) -> str:
    # 入口と出口の両方でNFCに揃える。どちらの形式を選ぶかより、
    # すべての比較が同じ形式を見ていることが重要。
    return unicodedata.normalize("NFC", str(p))
```

`list_dir`が返す値を正規化し、`read_file`が受け取る値を正規化し、
比較は正規化済みの形式のみで行います。ただし、分解形で保存されている
ファイルシステムに対して、正規化した文字列をそのままOSへ渡してはいけません。
自前で再構成した文字列を信頼せず、実際のディレクトリ一覧に対して解決してください。

## バイト長は文字数ではない

次に問題になるのは、文字数を数えている箇所すべてです。

ログ用にパスを切り詰める、名前の長さ制限をかける、表示幅に合わせて文字列を切る——
ASCIIでは安全なこれらの処理が、日本語では危険になります。日本語のファイル名は
UTF-8で1文字3バイトになることが普通なので、255バイトというファイルシステムの制限は
255文字ではありません。「安全な」200文字での切り詰めが、OSに拒否される名前を
生成しうるということです。さらに悪いことに、バイト位置で切ると
マルチバイト列の途中で分断され、不正なUTF-8が生成されます。
これは原因となったコードとまったく無関係な場所で例外になります。

切り詰めるなら、文字境界で切り、予算はバイトで持ちます。

```python
def clip(name: str, max_bytes: int = 200) -> str:
    b = name.encode("utf-8")
    if len(b) <= max_bytes:
        return name
    # バイト単位で切ってから、末尾の壊れた文字を捨てる。
    return b[:max_bytes].decode("utf-8", errors="ignore")
```

## レガシーエンコーディングの問題

そしてCP932があります。日本企業のファイルサーバには、Shift-JISで書き込む
ソフトウェアが何年も前に命名したファイルが相当数残っており、
そのバイト列は妥当なUTF-8ではありません。Linux上では、そもそもデコードできない
ファイル名として現れます。Pythonはサロゲートエスケープを返してきますが、
素朴な実装はディレクトリ走査の途中で`UnicodeDecodeError`を投げ、
`list_dir`の呼び出し全体を落とします。

ここで重要なのは、デコードできないファイルそのものではありません。
1件の不正なファイルのせいでツールが一覧ではなくエラーを返し、
その結果エージェントが「このディレクトリは読めない」と判断して、
残る400件のファイルで完了できたはずのタスクを諦めてしまうことです。
エントリ単位で防御的にデコードし、最悪の1件があっても一覧全体は生き残らせます。

```python
def safe_entries(d: Path) -> list[str]:
    out = []
    for entry in d.iterdir():
        try:
            out.append(canon(entry.name))
        except (UnicodeDecodeError, OSError):
            continue   # そのエントリだけ飛ばし、ディレクトリは使える状態に保つ
    return out
```

黙って飛ばすことは明確なトレードオフなので、ツール自身の出力で明示する価値があります。
私はスキップした件数を返すようにしています。そうすればモデルは
「402件のうち2件は読めませんでした」と言えます。ディレクトリが完全だったかのように
振る舞わせないためです。

## ツール引数に混入する全角文字

最後が個人的にいちばん厄介だと思っているもので、理由は目に見えないからです。
日本語入力では、ASCIIだと思っている文字の全角形が生成されます。`:`ではなく`：`、
`/`ではなく`／`、半角スペースではなく`　`（U+3000）です。日本語IMEを通して
パスが入力されたとき——あるいはモデルが日本語の文脈で見たパスを再現したとき——
通常のWindowsパスの中に全角コロンが紛れ込むことがあります。

正しく見えます。正しくありません。`NFKC`正規化はこれらをASCII等価物に畳み込みます。
これは**引数**に対しては望ましい挙動ですが、**ファイルの内容**に対しては絶対に
避けるべき処理です。NFKCは正当なテキストまで、誰も頼んでいない形に書き換えます。
引数はNFKCで正規化し、内容には触れないことです。

## なぜこれが重要になるのか

どれも技術的に難しい話ではありません。ただ、自分が「社内の文書フォルダを
エージェントが読めない」当事者になるまで見えないだけです。
そして英語で書かれた情報はほとんどありません。この問題に当たる人の多くが
日本語環境で作業しているからです。

丁寧に扱う価値があるのは、ファイルシステムのツールがその上のすべての土台に
なるからです。日本語文書を対象とするRAGパイプライン、日本語のコメントと
ファイル名を含むコードベースのリファクタリングを任されたエージェント、
社内記録を公開するMCPサーバ——いずれも同じ不親切な形で失敗します。
そして、いずれも「2階層下の文字列比較が間違っている」ではなく
「モデルが馬鹿なことをしている」という形で報告されます。

境界で正規化する。ファイルシステムがバイトで数えるなら、こちらもバイトで数える。
1つの不正なファイル名でディレクトリ一覧を落とさない。要点はほぼこれだけです。
